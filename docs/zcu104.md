# The ZCU104 (Zynq UltraScale+ XCZU7EV, DDR4 SODIMM, PS host)

The card's accelerator on AMD's ZCU104 evaluation board, built in Vivado 2025.2 (the XCZU7EV is in
the no-cost edition). The slice is the YPCB-00338's release r2 (variant m4) as it is: the same
`[arch]`, so the same arch_hash (4ffd1e17) and the same compiled programs. What changes is the
platform around it (`targets/zcu104.toml`, platform id 3).

Status (2026-10-31): the bitstream builds with every timing constraint met (WNS +0.085 ns, on
core_clk at 133.33 MHz: fmax 134.9 MHz) and the hardware platform (.xsa) is written. Since
2026-10-31 the accelerator, the merge and the DDR4 controller are cells of the block design (the
2026-10-29 build, with them in the RTL top, had WNS +0.266 ns and core_clk at 142.7 MHz; the
lower margin is not the synthesis mode: a build with every block design cell synthesized out of
context gave +0.093 ns on core_clk; the worst path is inside the accelerator, 92% of it routing). The memory path is checked in simulation (section 5). Not run on a board yet
(section 6).

## 1. The memory match

The card feeds the core from two DDR3-1066 channels of 64 bits: 2 x 1066 MT/s x 8 B = 17.06 GB/s.
The core takes one 128-byte chunk a cycle at 133.33 MHz: 17.07 GB/s. The ZCU104's PL SODIMM
(the board preset's MTA8ATF51264HZ-2G1, 4 GiB, 64 bits, tCK 938 ps = DDR4-2133) gives
2133 MT/s x 8 B = 17.06 GB/s, so at 133.33 MHz the core again asks for the memory's peak.

| | YPCB-00338 | ZCU104 |
|---|---|---|
| FPGA | xc7k480t-ffg1156-2 | xczu7ev-ffvc1156-2-e |
| Memory | 2 x DDR3-1066, LiteDRAM, host-calibrated | 1 x DDR4-2133 SODIMM, AMD DDR4 IP (MIG, PG150), self-calibrated |
| Host | x86 over PCIe Gen2 x8 (XDMA) | the PS's Cortex-A53s over AXI (HPM0, an AXI CDMA) |
| DSP cells | DSP48E1 (`rtl/tech/xilinx7`) | DSP48E2 (`rtl/tech/xilinxus`), cycle for cycle the same |
| Core clock | 133.33 MHz | 133.33 MHz |

## 2. What is new

- `rtl/boards/zcu104/otpu_mig_mux.sv`: the slice's two channels (one `otpu_mem_ch` each, two
  LiteDRAM-native ports a channel, the card's `otpu_native_sys` unchanged) merged onto the MIG's
  native interface in its ui_clk (266.5 MHz, one 512-bit beat a cycle). Channel c's beat a is the
  SODIMM's beat {a, c}, so a stream of chunks is a stream of consecutive beats. Round robin over the
  four ports into a registered two-entry queue (no combinational path from the MIG into
  `otpu_mem_ch`), a tag FIFO routing read data back in command order (ORDERING Strict), a write's
  data at or before its command, always full-beat writes.
- `rtl/boards/zcu104/otpu_zbd_tpu.v`, `otpu_zbd_mux.v`, `otpu_zbd_ddr4.v`: the block design's
  cells `tpu` (`otpu_native_sys` with its resets and LEDs), `merge` (`otpu_mig_mux`) and `ddr4`
  (the MIG with its native interface: the DDR4 IP's own block design cell offers only AXI), as RTL
  module references in Verilog-2001, so the whole design shows on the block design's canvas.
  `tpu` takes the target's parameters as its cell parameters (`create_project.tcl`); its defaults
  are the same values. The block design synthesizes globally (in `synth_1`), so these cells build
  as RTL in the top did: with `SYNTHESIS` defined, `act_uram.xdc` and `synth_1`'s retiming.
- `rtl/boards/zcu104/otpu_fpga_top_zcu104.sv`: the board's pins around the block design.
- `boards/zcu104/vivado/bd_zcu104.tcl`: the PS as host. On M_AXI_HPM0_FPD the control registers
  at 0xA000_0000 (the card's BAR0 0x0), the AXI CDMA at 0xA002_0000 (host <-> card copies between
  the PS DDR and the card DRAM at 0x10_0000_0000 + card address; 128-bit bursts, no DRE: 64-byte
  aligned copies, `otpu_mem_ch`'s contract), the SYSMONE4 at 0xA003_0000 (the card's XADC). One
  MMCM on pl_clk0: core_clk 133.33 MHz, core_clk2x 266.67 MHz (the TMEM's pumped RAMs), xclk
  177.78 MHz (the PS ports and the CDMA).
- `boards/zcu104/vivado/mig.tcl`: the DDR4 IP as the board file presets it, native interface.
- `boards/zcu104/vivado/act_uram.xdc`: the activation RAM's 64 blocks and the trace buffer's 4 in
  UltraRAM (RAM_STYLE ULTRA, plain set_property lines: Vivado's XDC reader drops Tcl control flow);
  `build.tcl` fails if synthesis maps fewer than 68 URAM288.
- `boards/zcu104/constraints/`: the pins (CPU_RESET M11, LEDs D5 D6 A5 B5 from the board file's
  part0_pins.xml) and the late timing constraints: the clocks, the calibration-done and reset
  crossings, and CDC waivers each naming the protocol that makes the crossing safe.
- `sim/verilator/otpu_mig_model.sv`, `otpu_migmem.sv`: a model of the MIG's user interface
  (app_rdy and app_wdf_rdy withheld at random, refresh stalls, in-order reads after a random
  latency) with checks on every rule the merge must keep, behind `otpu_mem_ch` and the merge,
  as `tb_board` MEM_NATIVE 3 (`SimTransport(native="mig")`).

Upstream files changed (all additive; the card's builds and simulations are unchanged):
- `boards/ypcb-00338/constraints/otpu_mem_ch.tcl` adds `g_xt.x_ripe_reg` to its existing waiver
  list (the same write-pointer crossing as the cells beside it, which Vivado reported as CDC-1 on
  the ZCU104 build; on the card the cell is the same, so the waiver covers it there too);
- `opentpu/target.py`: the zcu104 board's file list;
- `opentpu/host/board.py`, `sim/verilator/tb_board.sv`: the "mig" memory (MEM_NATIVE 3) beside
  the existing two;
- `sim/verilator/tb_board.sv`: the `TB_CTL_MRST` define, off by default, which holds the control
  master's reset (`ctl_mrst`) with `rst`, as the ZCU104's tpu cell does at configuration. Without
  it the testbench ties `ctl_mrst` to 0, as upstream, and a 4-state simulator never clears
  `otpu_axil_iso`'s `m_bvalid`.

## 3. Building

```
boards/zcu104/run_vivado.sh                  project, synthesis, implementation, bitstream
STEP=impl boards/zcu104/run_vivado.sh        implementation only
```

Two helpers in `boards/zcu104/vivado/`: `fit_check.tcl` (out-of-context synthesis of
`otpu_native_sys` alone: minutes, utilization by hierarchy) and `ip_probe.tcl` (the DDR4 IP's
ports and the configuration values `otpu_mig_mux` depends on).

Output in `build/zcu104/`: `otpu.bit`, `otpu.bin` (the raw configuration data, `write_cfgmem
-format bin -interface SMAPx32`; Linux's FPGA manager may want it through bootgen), `otpu_zcu104.xsa`
(the hardware platform for PetaLinux / Vitis) and `reports/SUMMARY.txt`. The build fails on a
synthesis critical warning, on fewer than 68 URAM, on any `CRITICAL WARNING` from the late
constraint files, or if a constraint file's summary line is missing.

## 4. Results

Block design build (2026-10-31, `build/zcu104_bd`, the accelerator, merge and DDR4 controller as
block design cells): every timing constraint met, WNS +0.085 ns on core_clk at 133.33 MHz (fmax
134.9 MHz), WHS +0.010 ns; 142,628 of 230,400 LUTs, 68 of 96 UltraRAM, 730 of 1,728 DSP48E2. The
worst path has 7 logic levels and is 92% routing. Three ZCU104 files changed after this build
(DDR4 interface metadata on the block design port). The one build on the final sources
(`OTPU_BD_OOC=1`, every block design cell synthesized out of context) met timing with core_clk
slack +0.093 ns (135.0 MHz).

Reports reviewed:
- report_cdc: no unwaived CDC-1, CDC-11 or CDC-13; 40 CDC-15 warnings (clock-enable controlled
  structures) and info-level synchronizers.
- report_methodology: 12 TIMING-54 critical warnings. They are the six clock-to-clock
  `set_max_delay -datapath_only ... -through` constraints per channel in the card's own
  `otpu_mem_ch.tcl` (the FIFO heads read across clocks), which TIMING-54 flags because the file
  is scoped to `otpu_mem_ch`. Each is narrowed by `-through` the FIFO RAM outputs, so no path
  outside the module matches it, and each tightens timing rather than relaxing it. The card's
  build uses the same file. Also 322 SYNTH-6 (RAM without an output register) and 7 LUTAR-1, all
  inside AMD IP (5 in the debug hub, 1 in the SYSMON core, 1 in the DDR4 PHY's PLL reset).
- report_drc: no errors. 44 DCIRST-1 on the SODIMM's POD12_DCI pins (the DDR4 IP as generated
  instantiates no DCIRESET; AMD answer record 000038677), DSP pipelining advisories (DPIP-2,
  DPOP-3, DPOP-4: the MXU's register placement is deliberate), and 3 PDCN-1569 plus 1 RTSTAT-10
  inside AMD's debug hub and DDR4 calibration logic.

## 5. Checked before hardware

`tests/test_zcu104.py`:
- the target has the card's `[arch]` and arch_hash, its sources exist and end with the top, and
  `create_project.tcl` and FuseSoC pass only parameters the top has;
- the card's demo programs on the board model through the ZCU104's memory path (`otpu_mem_ch`,
  `otpu_mig_mux`, the MIG model) at 0, 30 and 70 percent stalls: the results equal the ISA
  simulator's. Mutants of the merge (the channel bit dropped, a write command sent before its
  data, the byte mask inverted) fail it.

XSim replay (its scripts are not in this repository yet): openTPU's demo on `tb_board` with the
MIG model in Vivado XSim, the RTL compiled with `SYNTHESIS` defined, as Vivado builds it. That
removes the RTL's simulation-only zero initializers (`ifndef SYNTHESIS`), so registers with no
reset start as X. With unknown registers set to 0 at 1 ps (`xinit.tcl`, the FPGA's INIT and
Verilator's `--x-initial 0`), 14 instructions run in 9,083 cycles to halt and the memory read
back matches Verilator's byte for byte (3,932,160 bytes compared); a one-byte change is caught.
Without that pass, and with `TB_CTL_MRST`, the run stops making progress at about 85 us: the
quantizer waits on an arbiter grant that stays X through `otpu_tmem`'s unreset arbiter state
(`rpv <= lost`, and `lost` reads `rpv`). Zeroing `rpv` alone does not clear it. Random 0/1
power-up values are not tested.

## 6. Limits

- Not run on a board. The PS-side software (the host runtime over /dev/mem or UIO and the CDMA)
  is not written; `opentpu/host` drives the card over PCIe.
- The CAPS register's I2C bit is set as on the card, but the ZCU104 build ties the I2C pins high
  (no PL I2C bus is wired): software must not rely on it here.
